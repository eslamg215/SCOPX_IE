## What was added

- Migration `014_media_deletion_requests.sql` creates a tenant-scoped request inbox separate from `media_deletion_queue`.
- Request states are `submitted`, `under_review`, `approved`, `rejected`, and `cancelled`. An expiry state is intentionally omitted until an expiry policy is reviewed.
- A partial unique index allows only one open request per media asset. An approved request remains open until a future, separately reviewed enqueue workflow exists.
- Composite tenant/media and tenant/request foreign keys prevent cross-tenant references.
- Request facts (tenant, asset, requester, reason, submission time) are immutable.
- Database guards require an active tenant membership, enforce state transitions, require decision reasons, prohibit requesters from claiming or approving their own requests, and require the assigned reviewer to perform the final approval/rejection.
- A separate event table records submission and every state transition. Its rows reject UPDATE, DELETE, and TRUNCATE.
- The runtime role receives only SELECT/INSERT plus narrow UPDATE columns on requests, and SELECT-only access to events. Event inserts are generated by a database trigger; direct runtime event writes are denied.
- Tenant RLS is enabled and forced on both tables.
- PUBLIC execution is revoked from the SECURITY DEFINER trigger functions; they are intended to run only as installed triggers.

## Safety boundaries retained

- A request may be submitted while retention is unexpired or a legal hold is active because it is only a request for review.
- Approval does not enqueue work and does not bypass migration 011's queue guard.
- No API routes, queue insertion, scheduler, worker, metadata tombstoning, object-store operation, or physical deletion are enabled.
- No permission matrix for clinical roles is inferred here; API authorization remains blocked pending owner/governance review.
- CI uses disposable PostgreSQL and synthetic fixtures only.

## Verification planned in CI

- Migration ordering and explicit opt-in dependency.
- Request submission under active legal hold / unexpired retention without queue insertion.
- One-open-request uniqueness.
- Immutable request facts and valid/invalid state transitions.
- Requester/reviewer separation: requester self-claim is denied, and a distinct active tenant member must claim and decide (this is not a two-approver policy).
- Automatically recorded append-only event history.
- Cross-tenant RLS isolation for request and event tables.
- Least-privilege runtime grants and existing retention/legal-hold queue guards.

A passing CI run will validate only these automated schema/build checks. It will not certify the clinical product or authorize real patient-data use.
